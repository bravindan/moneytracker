# Taste
- Wants a full project scan before removing a feature, so the removal is complete (all references and the feature file itself gone, no dangling imports or orphaned files). Confidence: 0.6
- Prioritizes changes that "don't break the app and the rest of the logic" — expects verification (syntax/import/bundle checks) before the task is considered done. Confidence: 0.8
- Prefers removing a feature's files entirely (deleting orphaned components/screens) rather than leaving dead code behind. Confidence: 0.5
- Frequently pairs a feature request with a request to audit the surrounding existing implementation (e.g., "check if the fingerprint authentication implementation is well implemented") — expects correctness/security issues found in the review to be fixed, not just the requested feature. Confidence: 0.6
- Works on a named development branch (hermes-dev) and expects completed changes to be committed there rather than left uncommitted or merged to main. Confidence: 0.7
- Wants completed feature changes committed on the dev branch and then merged into master so the changes are reflected on both branches — the dev→master merge is explicitly requested, not avoided. Confidence: 1.0
- Wants commits to be attributed to their own GitHub account — no "Co-authored-by" bot trailer in commit messages. Confidence: 0.9
- Applies Expo-recommended dependency upgrades via `npx expo install` (using the exact compatible versions Expo specifies, e.g. expo@~57.0.9, react-native@0.86.2) rather than manually bumping packages. Confidence: 0.6
- Uses npm 11's `allow-scripts` allowlist (user-level `~/.npmrc` restricted to protobufjs) as a deliberate security measure — dependency installs must be made to work within this policy (e.g., project-level `.npmrc`/`allowScripts` entries) rather than bypassing it. Confidence: 0.7
- Prefers being handed the commands to run themselves (e.g., "give me the commands to run on my own") rather than having the agent execute project-affecting changes directly — the agent should hand off a clear command list. Confidence: 0.8
- Prefers separating shared/persistent UI (e.g., a screen header, a month-picker modal) into its own reusable component so it renders identically and stays mounted/available across all state branches (loading/empty/data) — UI that exists in only one state branch is a bug (e.g., a popup that appears only when the current month has data). This was demonstrated twice: the dashboard header and the month picker modal were both extracted into shared components rendered in every state. Confidence: 0.8
- Wants the agent to revert/remove any experimental modifications made during a task (e.g., created `.npmrc`, package.json edits) so the project is left in its original state, only touching what the agent itself changed. Confidence: 0.8
- Refactors must preserve the existing visual styling exactly — the user will notice and report styling regressions (e.g., a button losing its rounded corners after moving styles into a shared component) and expects the lost styles to be restored, not re-designed. Confidence: 0.6
- Wants end users to be kept informed of what changed with each release — an in-app changelog surfaced on new versions (e.g., a "What's New" entry with a badge until viewed) rather than silently shipping updates. Confidence: 0.5
- Prefers UI labels/copy to accurately describe the action they trigger — e.g., a button that fetches updates should say "Check for Updates", not the misleading "You're up to date". Confidence: 0.6
- Dislikes redundant/duplicate UI controls that perform the same function — when two buttons on one screen do the same thing (e.g., header "+ Add Record" and body "Create Monthly Record"), the duplicate should be removed to reduce clutter and keep a single entry point for the action. Confidence: 0.7
- Wants actions gated by state: controls that only make sense when data exists (e.g., the edit/delete record menu) should be hidden in the empty state, since you can't perform an action on a record that hasn't been created. Confidence: 0.7
